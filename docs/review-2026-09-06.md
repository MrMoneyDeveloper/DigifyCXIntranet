# Portal review — 6 September 2026

The review preserves the existing employee, HR, canteen, finance, and administration workflows and the current visual design. The checkout was fetched and pulled from `origin/main` before changes; both pointed to `e902fd9`. Existing local security and performance improvements were retained and verified alongside the additional fixes below.

## Hosting preserved

- Deployment scripts retain port `8080`, site name `DigifyCX Intranet`, and the documented friendly hostname `intranet.digifycx.local`.
- Deployment scripts, launch profiles, root settings files, and the existing local `web.config` were checked against 31 starting SHA-256 fingerprints and remain unchanged by this review.
- The actual production IIS binding and DNS state were not modified. Publishing to GitHub does not itself replace the IIS deployment.
- Runtime verification used the existing development port `5199`, an isolated review database, and synthetic accounts. Backend email, registry, and Zendesk integrations were disabled for those tests.

## Additional fixes

| Area | Finding and resulting behavior |
| --- | --- |
| Account activation | Verification grants now expire after 15 minutes and carry an Identity reset token bound to the verified account. Expired, replayed, revoked, or reassigned-account grants are rejected. |
| Password persistence | Password and activation status save together; failed Identity updates are detached before audit persistence so rejected credential mutations cannot accidentally be saved. |
| Ambiguous identities | Activation and Zendesk resets reject multiple employees with the same matching name; webhook resets rotate concurrency stamps. |
| Sessions | Missing/unknown authentication sources are rejected; development sessions are accepted only in Development. Existing database-session revocation checks are retained. |
| Browser security | Malformed CSP reports return 400. Reports are bounded to 16 KiB even without Content-Length; server-level size rejections return 413. Enforced CSP preserves the configured internal HTTP mode, while HTTPS responses retain resource-upgrade protection. |
| Private key storage | The startup guard rejects key storage equal to or beneath the web root, including paths with trailing separators. |
| Error handling | Anonymous failures can render the generic error page without a sign-in redirect. The page provides a request ID and recovery link instead of developer setup instructions. |
| Disabled integrations | Disabled registry synchronization no longer requires a populated URL. Enabled synchronization still requires an absolute HTTPS endpoint. |
| Home-page query | Monthly canteen totals use an indexed timestamp range instead of applying year/month functions to every order. Abandoned home-page requests propagate cancellation. |
| Reports | Paging has a unique tie-breaker, end dates include the whole selected day, maximum dates do not overflow, and retrieval enforces the existing 25,000-row export cap. Totals continue to cover the full filtered result. |
| News feed | Individual unavailable or malformed stories do not discard usable results. Total failure preserves the prior cache and reports failure to the scheduler. Empty feeds display a clear message. |
| Financial jobs | Completed batches remain idempotent. Failed or incomplete runs are reported as failures on retry; exports are not automatically resent when outbox persistence may already have succeeded. |
| Usability | Correct current-page navigation, a skip link, visible keyboard focus, reduced-motion support, usable narrow-screen navigation, properly associated form labels, visible submission errors, and preserved canteen selection. |
| Assets and dependencies | Removed an orphan stylesheet request, retained the locally built Tailwind asset, deferred/lazily loaded appropriate assets, and updated the vulnerable transitive `nanoid` dependency. |
| CI | Separate dependency-audit steps fail correctly; client build and migration commands propagate failures; publish output is scanned for accidental secrets and environment files. |

## Operational notes

Existing legacy cookies may require one fresh sign-in after deployment. Users with an old activation page should restart activation to receive the new short-lived verification grant.

If a financial batch is incomplete, inspect both its run record and the email outbox before recovery. A queue operation may have succeeded before a later database write failed. Automatic resend remains disabled to avoid duplicate financial exports; the failure is now visible to monitoring instead of being silently treated as success.

Review and apply the existing operational migration before deploying source that depends on its tables. No new migration was introduced by this review. Keep the current site's environment settings, binding, and hostname during normal deployment.

The key-storage review follows Microsoft's guidance on [data-protection key storage](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/implementation/key-storage-providers?view=aspnetcore-8.0) and [Windows key encryption](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/implementation/key-encryption-at-rest?view=aspnetcore-8.0).
